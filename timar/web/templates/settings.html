A guest needs no MAC of its own — it is started with qm, not a magic packet — but it is on-demand whenever its hypervisor is, so being off is never reported as a fault. Updates reach it through its host: wake the hypervisor, start the guest, update, shut both back down in order.

A MAC marks the machine as on-demand: it shows as asleep rather than down when off, and updates wake it, update it, and shut it back down. A magic packet is a broadcast and only reaches its own segment — pick a relay for a machine in a different subnet (another site, an office network), or if Timar runs on a bridge network. The relay must be always on, already enrolled, and have python3 or wakeonlan.

OpenWrt has no default on purpose: an unattended upgrade can fill the overlay partition or land a kernel-module mismatch, and the machine that breaks is the one carrying the session you would repair it from. Leave this empty and the host is swept for logs but never updated.

Raise this for a host whose update pulls container images or rebuilds a DKMS module — both pass the default routinely. When the limit is reached the remote command is not stopped: it keeps running while the run is recorded as failed, and this host is left powered on rather than shut down mid-upgrade. Updates run one host after another, so a wedged machine delays the rest by whatever is set here.
